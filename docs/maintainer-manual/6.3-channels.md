# 6.3 Channels

Channels are the runtime messaging surface for player-to-player communication in the engine. They are loaded from bundle content, registered into a global channel registry, and executed synchronously at send-time using audience strategy objects.

This article is a maintainer-focused deep dive on **contracts, coupling points, and failure behavior** for channel support in the current `ranvier` dependency.

## 6.3.1 Core model and ownership

Channel behavior is distributed across these core components:

- `Channel` (`node_modules/ranvier/src/Channel.js`)
  - Message send pipeline, formatting, error classes.
- `ChannelManager` (`node_modules/ranvier/src/ChannelManager.js`)
  - Registry for channel names + aliases.
- `BundleManager.loadChannels` (`node_modules/ranvier/src/BundleManager.js`)
  - Bundle loader path for `channels.js` definitions.
- Audience strategy classes:
  - `ChannelAudience` (base)
  - `WorldAudience`
  - `PrivateAudience`
  - `PartyAudience`
  - `RoleAudience`
- `Broadcast` helpers (used by `Channel.send`) and `PlayerManager` lookups (used by audience implementations).

## 6.3.2 Bundle contract (`channels.js`)

Channels are loaded from `<bundle>/channels.js` during bundle feature loading.

Accepted export shape:

- A single channel object, or
- An array of channel objects.

Loader behavior (`BundleManager.loadChannels`):

1. require `channels.js`
2. resolve legacy loader function form through `_getLoader(loader, srcPath)`
3. normalize to array if needed
4. stamp `channel.bundle = bundle`
5. register each channel with `state.ChannelManager.add(channel)`

Implications:

- Missing `channels.js` in a bundle is valid (no channels loaded from that bundle).
- Shape validation is mostly deferred to `Channel` constructor/runtime behavior.

## 6.3.3 Boot-order placement and compatibility impact

In `BundleManager.loadBundle`, `channels.js` is loaded after `behaviors/` and before `commands/`.

Why this matters:

- Command modules that depend on channels generally expect channels to already be present.
- Reordering this feature can shift startup/runtime failure timing and is compatibility-sensitive.

## 6.3.4 `Channel` instance contract

Required constructor fields:

- `name` (string)
- `audience` (object implementing audience contract)

Optional fields:

- `description`
- `minRequiredRole`
- `color` (string or array)
- `aliases`
- `formatter` (`{ sender, target }`)
- `bundle` (set by loader for traceability)

Constructor-enforced guards:

- Missing `name` => throw
- Missing `audience` => throw

Default formatter behavior:

- sender view and target view both use `[channel] sender: message` unless overridden.

## 6.3.5 Audience strategy contract

Base `ChannelAudience` contract:

- `configure({ state, sender, message })`
- `getBroadcastTargets()`
- optional `alterMessage(message)`

Built-in audience semantics:

- `ChannelAudience` (base): all players from `PlayerManager.getPlayersAsArray()`.
- `WorldAudience`: all players except sender (`PlayerManager.filter`).
- `PrivateAudience`:
  - target is first token from message
  - lookup via `PlayerManager.getPlayer(targetName)`
  - `alterMessage` removes target token
- `PartyAudience`: sender’s party members excluding sender; empty when sender has no party.
- `RoleAudience`: players with role `>= minRole`, excluding sender.

Operational caveat:

- Audiences rely on `configure` being called first; `Channel.send` currently guarantees that ordering.

## 6.3.6 Send pipeline (end-to-end)

`Channel.send(state, sender, message)` runs synchronously:

1. Reject empty message (`NoMessageError`).
2. Ensure audience exists.
3. `audience.configure(...)`.
4. Resolve targets via `getBroadcastTargets()`.
5. Special-case failures:
   - party audience + no targets => `NoPartyError`
   - private audience + no target => `NoRecipientError`
6. Allow audience to mutate message (`alterMessage`).
7. Echo to sender via formatter.
8. Broadcast to audience recipients via `Broadcast.sayAtFormatted(...)`.
9. Emit `channelReceive(channel, sender, rawMessage)` on each target, where `rawMessage` has color tags stripped.

Key invariants:

- Sender echo happens before recipient loop.
- `channelReceive` payload is raw (tag-stripped), not rendered text.

## 6.3.7 Registry semantics (`ChannelManager`)

`ChannelManager` stores channels in `Map` under:

- canonical channel name
- each alias (mapped to same channel object)

Core methods:

- `get(name)`
- `add(channel)`
- `remove(channel)`
- `find(prefix)` (linear prefix search)

Important edge behavior:

- `remove(channel)` deletes only canonical name; aliases are not removed.
- Alias collisions overwrite prior map entries silently.
- `find` returns first insertion-order prefix match, making ambiguous prefixes load-order-sensitive.

## 6.3.8 Error and failure behavior

Typed channel errors:

- `NoMessageError`
- `NoRecipientError`
- `NoPartyError`

Other failure classes:

- Generic error on invalid audience object at send-time.
- Audience implementation errors bubble through send path (no local catch in `Channel.send`).

Maintainer takeaway:

- Bad channel/audience code is fail-fast and synchronous; failures can interrupt command flow unless caught by command layer.

## 6.3.9 Coupling points and integration boundaries

Channels depend on:

- `PlayerManager` APIs used by audience strategies (`getPlayersAsArray`, `filter`, `getPlayer`).
- `Broadcast` rendering/output behavior.
- Party state (`sender.party`) for party audience.
- Role values on player for role audience.

Channels provide:

- User-facing communication output.
- `channelReceive` event signal on recipients for script/behavior hooks.

Because `channelReceive` is emitted on targets, channels are also an event bridge into entity/player scripting logic.

## 6.3.10 Performance characteristics

Cost profile of a send:

- Audience target resolution cost depends on audience strategy.
- Broadcast + event emit is O(number of recipients).
- `find(prefix)` and some audience filters are linear scans.

Hot-path guidance:

- High-volume channels should avoid expensive custom audience logic.
- Avoid unnecessary formatting work in custom formatters on large broadcasts.

## 6.3.11 Security and trust boundaries

Risk areas:

- Channel message content is player input and may include engine color tags.
- Bundle channel definitions are loaded via dynamic `require`.
- Custom audience/formatter code executes in-process with full runtime access.

Observed safeguards in core path:

- Raw `channelReceive` message strips simple tags via regex before emit.
- No eval-like behavior in channel classes themselves.

Limitation:

- Tag stripping is simple (`/<\/?\w+?\>/gm`) and not a full sanitizer.

## 6.3.12 High-priority gotchas

1. `ChannelManager.remove` leaves aliases behind (stale alias references).
2. `colorify` uses `reverse()` on color array; behavior can be surprising if color arrays are reused/inspected.
3. `formatToReceipient` is misspelled but used as internal default method name.
4. Private-audience parsing is token-based and assumes first token is target name.
5. Ambiguous channel prefix resolution (`find`) depends on insertion order.
6. Channel config shape is lightly validated; malformed custom formatters fail late.

## 6.3.13 Suggested regression tests

1. `loadChannels` supports both single-object and array exports.
2. Constructor validation throws for missing `name`/`audience`.
3. `PrivateAudience` path:
   - missing target => `NoRecipientError`
   - target token stripped from delivered message
4. `PartyAudience` path:
   - no party => `NoPartyError`
5. `channelReceive` emits tag-stripped raw message.
6. `ChannelManager.remove` alias behavior (document current semantics and guard desired future fix).
7. Prefix lookup ambiguity test to lock or improve deterministic behavior.

## 6.3.14 Operational debugging checklist

When channel send fails unexpectedly:

1. Confirm channel is registered under expected key/alias in `ChannelManager.channels`.
2. Confirm `audience.configure` is receiving `{ state, sender, message }`.
3. Inspect resolved target count before broadcast.
4. Verify formatter functions exist and return strings.
5. Check whether failure is from channel error class vs audience/custom code throw.

When recipients do not react to channel events:

1. Confirm recipients are in resolved target list.
2. Verify `channelReceive` listeners are attached on target entities/players.
3. Confirm message expected by listener is raw (tags stripped), not formatted display text.

---

### Maintainer note

Channels look simple but they are a compatibility-sensitive cross-cutting surface (command UX, player communication, moderation/admin tooling, scripting hooks). Changes should be treated as integration changes, with explicit tests around registration, routing, and error semantics.
