# 6.3 Quest Goals

Quest goals are the quest-objective extension point loaded from each enabled bundle’s `quest-goals/` directory. In core, they are class-based runtime objects that subscribe to gameplay events and report progress back to their parent `Quest` instance.

This section is intended as the **maintainer-facing companion** to bundle author docs: it explains the runtime contracts, load order dependencies, and failure modes that matter when operating or changing boot/integration behavior.

## 6.3.1 Core model and ownership

Core components involved in quest goals:

- `QuestGoal` (`node_modules/ranvier/src/QuestGoal.js`)
  - Base class (`EventEmitter`) for individual goal instances.
  - Provides default no-op behavior and persistence hooks.
- `QuestGoalManager` (`node_modules/ranvier/src/QuestGoalManager.js`)
  - Registry keyed by goal type name; implemented as `Map`.
- `BundleManager.loadQuestGoals` (`node_modules/ranvier/src/BundleManager.js`)
  - Discovers and registers goal classes from `quest-goals/`.
- `QuestFactory.create` (`node_modules/ranvier/src/QuestFactory.js`)
  - Resolves goal type names and instantiates concrete goal objects.
- `Quest` (`node_modules/ranvier/src/Quest.js`)
  - Aggregates progress across goals and drives turn-in/complete events.
- `QuestTracker` + `Player.emit` (`node_modules/ranvier/src/QuestTracker.js`, `node_modules/ranvier/src/Player.js`)
  - Fan out gameplay events to active quests/goals.

## 6.3.2 Bundle contract (`quest-goals/`)

Each goal module is loaded from `bundles/<bundle>/quest-goals/*.js` during bundle feature load.

Type keying rules:

- Goal type key is filename stem.
  - Example: `quest-goals/kill-rat.js` => type key `kill-rat`.
- Quest YAML goal entries must reference this key in `goals[].type`.

Accepted module forms (compatibility behavior in core):

1. Direct class export where `QuestGoal.isPrototypeOf(loader)` is true.
2. Legacy loader function export `module.exports = (srcPath) => GoalClass`.

Registration flow (`BundleManager.loadQuestGoals`):

- script file detection via `Data.isScriptFile(...)`
- require module
- resolve import form
- `state.QuestGoalManager.set(goalName, goalImport)`

Operational implication:

- Missing `quest-goals/` is valid (no goals registered by that bundle).
- Invalid/missing goal types are typically discovered later at quest instantiation, not registration time.

## 6.3.3 Boot/load ordering guarantees

Quest-goal load order is a hard contract in `BundleManager.loadBundle`:

1. `quest-goals/`
2. `quest-rewards/`
3. other feature surfaces
4. area/help loading

Why this matters:

- Areas/quests can safely reference goal types because registries are populated before quest definitions are instantiated.
- Reordering this feature list is compatibility-impacting: it changes when unresolved goal types fail.

## 6.3.4 Runtime lifecycle (end-to-end)

1. Bundle loads goal classes into `QuestGoalManager`.
2. Quest definitions are loaded into `QuestFactory`.
3. When a quest instance is created (`QuestFactory.create`):
   - `Quest` instance is created
   - each configured goal becomes `new goalType(instance, goal.config, player)`
   - each goal is attached with `goal.on('progress', () => quest.onProgressUpdated())`
4. Player emits gameplay events.
5. `Player.emit` forwards to `questTracker.emit`.
6. `QuestTracker.emit` forwards to each active quest.
7. `Quest.emit` forwards to each goal (except `progress`).
8. Goal updates internal state and emits `progress`.
9. `Quest` recomputes aggregate progress and emits:
   - `progress` while incomplete
   - `turn-in-ready` when >= 100% and not auto-complete
   - `complete` when >= 100% and auto-complete

## 6.3.5 Goal instance contract

`QuestGoal` constructor input:

- `quest`: parent quest instance
- `config`: per-goal config payload from quest definition
- `player`: owning player

Expected overridable methods:

- `getProgress(): { percent: number, display: string }`
- `complete(): void`
- optional event listeners attached internally by goal implementation

Persistence hooks:

- `serialize()` returns `{ state, progress, config }`
- `hydrate(state)` restores `this.state`

Default behavior worth remembering:

- Base `getProgress()` returns 0% and warning display text.
- If goal implementation forgets to override progress, quests never complete via that goal.

## 6.3.6 Aggregation semantics and event routing

Quest progress computation in `Quest.getProgress()`:

- Sums each goal’s `percent`
- Averages by `goals.length`
- Joins `display` strings with `\r\n`

Event routing semantics:

- `Quest.emit` proxies all events to goals except `progress` (to avoid recursion loops).
- `QuestTracker.emit` proxies arbitrary player events to every active quest.

This makes goal behavior event-driven by default: if gameplay systems emit events consistently, goals can subscribe without tight coupling to command handlers.

## 6.3.7 Persistence/hydration behavior

Serialization path:

- `Player.serialize()` includes `quests: questTracker.serialize()`.
- `QuestTracker.serialize()` stores active quests as `[qid, quest.serialize()]`.
- `Quest.serialize()` stores goal state as ordered array.

Hydration path:

- `Player.hydrate(...)` hydrates quest tracker early (before other hydration steps).
- `QuestTracker.hydrate(...)` recreates each quest via `QuestFactory.create(...)`, restores `started`, and calls `quest.hydrate()`.
- `Quest.hydrate()` replays state by index (`goals[i].hydrate(goalState.state)`).

Ordering invariant:

- Goal state hydration is positional, not keyed. Reordering goal definitions for an existing quest can misapply saved state.

## 6.3.8 Error behavior and failure modes

### Hard failures (throws)

- `QuestFactory.canStart` throws on invalid quest id.
- `QuestFactory.create` throws on invalid quest id.
- `QuestTracker.complete` throws when quest not active.

### Soft/late failures

- Missing goal class for configured `goal.type` usually fails at constructor invocation in `QuestFactory.create`.
- Goal modules are not strongly schema-validated during load, so malformed exports may surface at runtime.

### Semantics traps

- Quest with zero goals yields divide-by-zero average (`NaN`) in `Quest.getProgress()`.
- `Quest.serialize()` includes `config.desc`, while config defaults use `description`; mismatch can drop expected text in serialized metadata.

## 6.3.9 Compatibility-sensitive behaviors

Treat these as externally observable contracts:

- Feature order with `quest-goals/` early in bundle load.
- Type key derivation from goal filename.
- Event relay chain (`Player -> QuestTracker -> Quest -> Goal`).
- Aggregate progress threshold (`>= 100`) for turn-in/complete behavior.
- Goal state positional hydration.

Changing any of these requires explicit compatibility review and test coverage.

## 6.3.10 Performance characteristics

Hot-path cost model:

- Every player event fans out to all active quests.
- Every active quest fans out that event to all of its goals.

So effective dispatch work is approximately:

- `O(activeQuests * goalsPerQuest)` per relevant player event.

Additional cost centers:

- `Quest.getProgress()` recomputes by iterating all goals each progress update.
- Listener count grows with active goal instances.

For large quest counts, prefer goal logic that emits `progress` only on meaningful state changes.

## 6.3.11 Maintainer guardrails

1. Keep quest goal type names stable; filename changes are compatibility changes.
2. Add explicit validation in load/create paths before making behavior changes:
   - verify goal import shape at registration
   - verify goal type exists before constructor call
3. Preserve hydration ordering assumptions unless migration tooling is added.
4. Treat event names consumed by goals as contract surface; avoid silent renames in gameplay emitters.
5. Add regression tests before touching:
   - load order
   - progress aggregation semantics
   - quest state serialization/hydration

## 6.3.12 Suggested tests to add in wrapper or core CI

- Goal load registration:
  - class export and legacy loader export both register correctly.
- Missing goal type:
  - quest instantiation reports clear, contextual error.
- Zero-goal quest:
  - lock expected behavior (`NaN` or future guarded fallback).
- Hydration ordering:
  - reordered goal definitions demonstrate state mismatch (documented or guarded).
- Event fanout:
  - player event reaches goal listener through full relay chain.

## 6.3.13 Quick debugging checklist

When quest goals are “not progressing”:

1. Verify goal type exists in runtime registry (`QuestGoalManager.keys()`).
2. Verify quest definition `goals[].type` matches filename stem exactly.
3. Verify expected gameplay event is emitted on `Player` (and not blocked by prune/hydration guards).
4. Verify goal listener updates state and emits `progress`.
5. Inspect active quest `serialize()` output for stale or mismatched state shape.

When quest completion triggers but rewards/state seem wrong:

1. Confirm aggregate percent from `Quest.getProgress()`.
2. Confirm `autoComplete` vs turn-in flow.
3. Confirm `QuestTracker.complete(...)` path and saved quest tracker payload.

---

### Maintainer note

Quest goals are one of the most coupling-heavy extension surfaces in the runtime because they sit at the intersection of:

- bundle code loading,
- player event topology,
- quest state persistence,
- and completion/reward flow.

For this reason, changes should default to **validation + tests + explicit compatibility notes** rather than refactor-first approaches.
